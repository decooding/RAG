Ниже представлена спецификация требований и критерии приёмки (**Definition of Done — DoD**) для каждого модуля вашего RAG-проекта.

Этот документ служит прямым техническим заданием для вашего **Агента-разработчика** и чек-листом для проверки с моей стороны в роли **Контролёра**.

---

### Архитектурная карта проекта

```
src/
├── data/          # Модуль 1: Чанкинг и парсинг документов (НПА РК)
├── indexing/      # Модуль 2: Векторизация и хранение (ChromaDB + BM25)
├── retrieval/     # Модуль 3: Поисковый движок и гибридный поиск
├── generation/    # Модуль 4: LLM-пайплайн и промпт-инжиниринг (Gemini Flash)
├── benchmark/     # Модуль 5: Замеры скорости и метрики качества (Hit@k, Latency)
└── reporting/     # Модуль 6: Экспорт графиков и LaTeX-таблиц для диссертации
```

---

### Модуль 1. Data & Preprocessing (`src/data/`)

> **Назначение:** Парсинг документов нормативно-правовых актов (кодексы РК), структурный и наивный чанкинг, подготовка метаданных.

* **Требования к реализации:**
  * Поддержка двух стратегий чанкинга для сравнительного эксперимента:
    1. **Structural Chunking:** Строго по статьям (один чанк = одна статья, метаданные: `article_number`, `article_title`, `chapter`, `section`).
    2. **Naive Chunking:** Разбиение фиксированным окном (например, 500 и 1000 символов с перекрытием 10–15%) для сопоставления в диссертации.
  * Очистка от мусорных переносов строк внутри предложений при сохранении структуры списков и пунктов (1), 2), а)).
  * Исключение преамбул и фильтрация утративших силу статей (флаг `is_repealed`).

* **Definition of Done (DoD):**
  * [ ] Выходной формат — строго валидный список словарей / dataclass объектов с типизацией.
  * [ ] Метаданные не содержат значений `None` (приведены к типам `str`, `int`, `bool`).
  * [ ] Скрипт успешно отрабатывает без падений на полном тексте любого кодекса РК.
  * [ ] Итоговый JSON сохраняется в директорию `data/processed/` с логом статистики (число статей, средняя длина символов).

### Модуль 2. Indexing & Storage (`src/indexing/`)

> **Назначение:** Создание и персистентное сохранение векторных индексов (ChromaDB) и лексического индекса (BM25).

* **Требования к реализации:**
  * Изоляция векторных коллекций под разные эксперименты:
    * `rk_articles_dense_gemini` (эмбеддинги `text-embedding-004`);
    * `rk_articles_dense_local` (эмбеддинги `multilingual-e5-small` для сравнения);
    * `rk_articles_naive_500` (наивные чанки для сравнения).
  * Пакетная загрузка (батчинг по 50–100 документов) с обработкой сетевых исключений при обращениях к API эмбеддингов.
  * Реализация и сериализация индекса BM25 (`rank_bm25`) на диск (через `pickle`) для быстрого переиспользования без повторной токенизации.

* **Definition of Done (DoD):**
  * [ ] Данные ChromaDB сохраняются в локальную папку (`PersistentClient`), база перечитывается при перезапуске без переиндексации.
  * [ ] Количество документов в коллекции строго совпадает с числом чанков из Модуля 1.
  * [ ] Все строковые и числовые метаданные сохранены и доступны для фильтрации (`where={"article_number": ...}`).

### Модуль 3. Retrieval Engine (`src/retrieval/`)

> **Назначение:** Поиск релевантного контекста по запросу пользователя (Lexical, Dense, Hybrid).

* **Требования к реализации:**
  * Единый интерфейс функции/класса поиска: `retrieve(query: str, top_k: int, mode: str) -> List[SearchResult]`.
  * Реализация трёх режимов:
    1. `mode="bm25"`: Только поиск по ключевым словам.
    2. `mode="dense"`: Семантический поиск по векторной базе Chroma.
    3. `mode="hybrid"`: Слияние результатов (например, метод Reciprocal Rank Fusion — RRF).
  * Объект результата `SearchResult` должен обязательно возвращать: `text`, `metadata`, `score` (или ранг) и `retrieval_time_ms`.

* **Definition of Done (DoD):**
  * [ ] Время поиска измеряется строго через `time.perf_counter()` и логируется отдельно от сетевых запросов LLM.
  * [ ] При пустом или бессмысленном запросе модуль возвращает пустой список, а не бросает `Exception`.
  * [ ] Для всех найденных чанков гарантированно сохраняется связь с исходным номером статьи.

### Модуль 4. Generation Pipeline (`src/generation/`)

> **Назначение:** Формирование промпта, вызов Gemini 1.5 Flash и генерация юридически строгого ответа с источником.

* **Требования к реализации:**
  * Шаблон системного промпта должен требовать строгой опоры на контекст: *«Отвечай исключительно по предоставленным статьям. Если информации нет, скажи, что норма не регулируется данными статьями. Обязательно указывай номер статьи»*.
  * Поддержка стриминга (`client.models.generate_content_stream`) для фиксации метрики **TTFT** (Time-to-First-Token).
  * Фиксация температуры генерации (`temperature=0.1 – 0.2`) для обеспечения воспроизводимости экспериментов.

* **Definition of Done (DoD):**
  * [ ] Скрипт корректно замеряет два раздельных тайминга:
    * `ttft_ms`: миллисекунды от отправки промпта до получения первого чанка токенов;
    * `total_gen_time_ms`: полное время формирования ответа.
  * [ ] Обработаны сетевые ошибки API и лимиты запросов (rate limits) с механизмом `retry / exponential backoff`.
  * [ ] Ответ возвращается в структурированном виде: `{ "answer": str, "citations": list, "ttft_ms": float, "total_ms": float }`.

### Модуль 5. Benchmark & Evaluation (`src/benchmark/`)

> **Назначение:** Автоматический прогон тестового датасета, расчет академических метрик и сбор сырых данных.

* **Требования к реализации:**
  * Загрузка эталонного датасета (`test_dataset.json`) с полями: `query_id`, `question`, `target_article`, `ground_truth_answer`.
  * Расчет стандартных метрик информационного поиска:
    * **Hit@K** (попала ли целевая статья в Top-K выдачи: $k \in \{1, 3, 5\}$);
    * **MRR (Mean Reciprocal Rank)**;
    * **Precision@K** и **Recall@K**.
  * Замер аппаратных/временных метрик: `retrieval_latency`, `generation_latency`, `e2e_latency`, `tokens_per_sec`.

* **Definition of Done (DoD):**
  * [ ] Скрипт выполняет «холодный старт» (прогрев базы 1–2 запросами перед основными замерами, чтобы исключить искажение таймингов).
  * [ ] Результаты каждого прогона сохраняются в `results/raw_runs/{timestamp}_run.csv` со всеми промежуточными полями.
  * [ ] Подсчитанные агрегированные метрики выводятся в консоль в виде сводной таблицы.

### Модуль 6. Reporting & Visualizations (`src/reporting/`)

> **Назначение:** Формирование артефактов для текста диссертации и научной статьи.

* **Требования к реализации:**
  * Скрипт на `matplotlib` / `seaborn`, генерирующий векторные графики (PDF/PNG 300 DPI) с читаемым академическим шрифтом (без засечек, строгие оси).
  * Графики:
    1. Зависимость Hit@k от стратегии поиска (BM25 vs Dense vs Hybrid).
    2. Зависимость Latency (задержки) от размера чанка (500 vs 1000 vs постатейный).
  * Генератор сводной таблицы в формате синтаксиса **LaTeX (`booktabs`)** для прямой вставки в Overleaf/Word.

* **Definition of Done (DoD):**
  * [ ] Графики сохраняются в папку `results/plots/` в разрешении, пригодном для печати.
  * [ ] Сгенерированный LaTeX-код компилируется без ошибок разметки таблиц.
